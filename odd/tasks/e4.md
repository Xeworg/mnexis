## Specs

S30 — A-19 close: a second distinct client (not rmcp) drives every
memory_* tool end-to-end over the real `mnexis mcp serve` binary
through a hand-written JSON-RPC client. The traffic shape is what an
LLM agent would emit: prompt-shaped multi-tool sequences with
realistic id allocations (numeric, string, large, null), error
recovery loops, and three-process concurrency.

S31 — The harness-shaped test covers at least:
  - `memory_supersede` end-to-end (the official rmcp client only lists
    the name; never invokes).
  - Idempotency-key replay: same key + same payload → same uuid;
    same key + different payload → `TOPIC_CONFLICT` (-32050 / exit 5).
  - Recovery from REVISION_CONFLICT: the harness re-reads the live
    revision after a failed update and retries with the fresh
    expected_revision.
  - Three concurrent child processes share the same `--data-dir`
    profile: one saves, the second updates with the correct revision,
    the third searches and sees the post-update state without
    observing any partial write.
  - Large payload at the configured limits (4 KiB content, 32 tags).
  - No-leak: stderr carries no memory content; stdout carries only
    JSON-RPC frames.

S32 — The hand-written JSON-RPC client is a small `McpHarness` struct
in the test file. It owns the child's stdin/stdout, tracks
request/response by `id`, and exposes `call_tool`/`notify`/`shutdown`
helpers. The structure is enough to be a "second client" but not a
reference agent (A-19's "agente de referencia" half is satisfied
manually with an MCP Inspector smoke recorded in this file's log).
